01 — Flashcards — cliquer pour retourner
🃏
Concepts clés du déploiement
DEBUG = True en production↻
Faille de sécurité critique — expose le code source, les variables d'env. et la config en cas d'erreur. Toujours False en prod.
DNS↻
Domain Name System — traduit un nom de domaine (monprojet.com) en adresse IP (162.55.12.48). L'annuaire d'internet.
SECRET_KEY dans Git↻
Faille de sécurité majeure. La clé secrète doit être dans un fichier .env ignoré par Git, et lue via python-decouple ou os.environ.
Pré-production (staging)↻
Environnement identique à la prod mais avec des données de test. Permet de valider les changements avant que les vrais utilisateurs les voient.
Gunicorn↻
Serveur WSGI Python pour la production. python manage.py runserver est uniquement pour le développement local — jamais en prod.
CNAME record↻
Enregistrement DNS qui crée un alias — pointe un domaine vers un autre. www.monprojet.com → xxx.up.railway.app
collectstatic↻
python manage.py collectstatic copie tous les fichiers statiques dans STATIC_ROOT pour qu'ils soient servis par WhiteNoise ou un CDN en prod.
WhiteNoise↻
Package Python qui permet à Django de servir ses propres fichiers statiques en production — sans avoir besoin de Nginx. Ajouter dans MIDDLEWARE.
Propagation DNS↻
Délai entre la configuration d'un DNS et sa visibilité mondiale. Peut aller de quelques minutes à 48 heures selon les TTL des serveurs.
PaaS vs VPS↻
PaaS (Railway, Render) : déploiement depuis Git, zéro admin serveur, idéal pour débuter. VPS : serveur nu à configurer, plus de contrôle, plus complexe.

04 — Scénarios de production — que faites-vous ?
Scénario 1 — DisallowedHost
🚀 Tu viens de déployer sur Railway. En accédant à l'URL ton-projet.up.railway.app, tu obtiens l'erreur : DisallowedHost at / Invalid HTTP_HOST header. Que fais-tu ?
Mettre DEBUG = True pour désactiver la vérification
Ajouter ton-projet.up.railway.app dans la variable d'environnement ALLOWED_HOSTS sur Railway
Redéployer le projet depuis zéro
✓ DisallowedHost signifie que Django reçoit une requête depuis un domaine qui ne figure pas dans ALLOWED_HOSTS. En production, ce paramètre doit contenir exactement les domaines autorisés. Mettre DEBUG=True pour contourner est dangereux — ça expose tout le code source en cas d'erreur.
Scénario 2 — Fuite de secrets
🔐 En relisant ton code avant de pousser sur GitHub, tu réalises que ton fichier settings.py contient en clair SECRET_KEY = 'django-insecure-abc123'. Tu n'as pas encore committé. Que fais-tu ?
Committer quand même — ce n'est que la clé de développement
Déplacer la clé dans un fichier .env, la lire avec python-decouple dans settings.py, et vérifier que .env est dans .gitignore avant de committer
Renommer le fichier settings.py pour qu'il ne soit pas versionné
✓ Même une clé de dev en clair sur GitHub public sera collectée par des robots en quelques minutes. La bonne pratique : toujours dans .env, toujours dans .gitignore, lue via python-decouple ou os.environ. Si tu as déjà committé une clé secrète sur GitHub : la régénérer immédiatement avec get_random_secret_key() et purger l'historique Git.
Scénario 3 — CSS manquant en prod
🎨 Ton projet fonctionne sur Railway mais toutes les pages s'affichent sans CSS — les styles ne chargent pas (erreur 404 sur les fichiers .css). Quelle est la cause la plus probable ?
Le CSS est trop volumineux pour Railway
WhiteNoise n'est pas installé ou pas ajouté dans MIDDLEWARE, et/ou collectstatic n'a pas été exécuté dans la commande de démarrage
Il faut désactiver HTTPS pour que les fichiers statiques se chargent
✓ En production, Django ne sert pas les fichiers statiques lui-même (contrairement au mode DEBUG). WhiteNoise doit être dans MIDDLEWARE (avant SessionMiddleware), STATICFILES_STORAGE doit pointer vers WhiteNoise, et la commande de démarrage doit inclure python manage.py collectstatic --noinput avant gunicorn.
Scénario 4 — Domaine personnalisé
🌐 Tu as acheté monblog.fr sur OVH. Tu l'as configuré en CNAME vers ton URL Railway il y a 20 minutes. Mais monblog.fr n'affiche pas encore ton projet. Que fais-tu ?
Supprimer le domaine et en racheter un autre
Contacter le support Railway car c'est de leur faute
Attendre — la propagation DNS peut prendre jusqu'à 48h. Vérifier la configuration sur dnschecker.org et s'assurer que monblog.fr est bien dans ALLOWED_HOSTS sur Railway
✓ La propagation DNS est un processus mondial qui prend du temps — c'est inhérent au fonctionnement d'internet, pas un bug. Vérifier sur dnschecker.org si le CNAME se propage correctement. Vérifier aussi que le domaine est dans ALLOWED_HOSTS, sinon Django renverra DisallowedHost même après propagation complète.

Étapes pour déployer sur Railway pour la première fois

⠿?Configurer les variables d'env. sur Railway (SECRET_KEY, DEBUG, ALLOWED_HOSTS)
⠿?Préparer settings.py : lire DEBUG/SECRET_KEY depuis les variables d'env.
⠿?Tester toutes les pages et vérifier les logs Railway
⠿?Créer requirements.txt, Procfile et vérifier .gitignore (.env absent)
⠿?Configurer la commande de démarrage (migrate + collectstatic + gunicorn)
⠿?Tester le projet en local et s'assurer que tout fonctionne

import dj_database_url

# Lire depuis le fichier .env ou les variables serveur
SECRET_KEY = config('')

# Domaines autorisés — séparés par des virgules dans .env

# PostgreSQL via DATABASE_URL, SQLite en local par défaut

    'default': dj_database_url.config(
        default=''
    )
