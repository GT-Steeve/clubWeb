Concepts clés de l'authentification
@login_required↻
Décorateur qui bloque l'accès d'une vue aux visiteurs non connectés
request.user↻
L'utilisateur connecté, disponible dans toutes les vues Django
user.is_authenticated↻
Retourne True si connecté, False si visiteur — utilisable dans les templates
UserCreationForm↻
Formulaire Django prêt à l'emploi pour créer un compte utilisateur
{% csrf_token %}↻
Tag obligatoire dans chaque formulaire POST — protection contre les attaques CSRF
LOGIN_REDIRECT_URL↻
Réglage dans settings.py — URL de redirection après une connexion réussie
save(commit=False)↻
Crée l'objet Python sans le sauvegarder en BDD — permet d'ajouter des champs avant
login(request, user)↻
Connecte l'utilisateur programmatiquement — utilisé après la création de compte
include('django.contrib.auth.urls')↻
Branche toutes les vues auth Django en une ligne dans urls.py
registration/login.html↻
Chemin exact attendu par Django pour le template de connexion

04 — Scénarios
Scénario 1
🧑‍💻 Un utilisateur visite /blog/creer/ sans être connecté. Que va-t-il se passer si la vue est décorée avec @login_required ?
Il voit une erreur 500 — le serveur plante
Il est redirigé vers la page de connexion automatiquement
Il voit le formulaire mais ne peut pas le soumettre
✓ @login_required redirige automatiquement vers LOGIN_URL (par défaut /accounts/login/). L'URL de retour est passée en paramètre pour revenir après connexion.
Scénario 2
🧑‍💻 Dans la vue d'inscription, vous avez form.save() au lieu de save(commit=False). Le champ auteur n'est pas dans le form. Que se passe-t-il ?
Django met automatiquement l'utilisateur connecté comme auteur
Erreur : le champ auteur est obligatoire et manque — la sauvegarde échoue
L'article est créé sans auteur — le champ reste vide
✓ save(commit=False) permet d'ajouter l'auteur avant la vraie sauvegarde. Sans ça, Django tente de sauvegarder un article sans auteur — ce qui viole la contrainte de clé étrangère.
Scénario 3
🧑‍💻 Dans votre template, vous masquez le bouton "Créer un article" avec {% if user.is_authenticated %}. Mais vous n'avez pas mis @login_required sur la vue. Est-ce suffisant ?
Oui — si le bouton est caché, personne ne peut accéder à la vue
Non — n'importe qui peut taper l'URL directement dans le navigateur
Ça dépend du navigateur utilisé
✓ Masquer dans le template est du côté affichage seulement. La protection réelle est @login_required sur la vue côté serveur. Les deux sont nécessaires.
Scénario 4
🧑‍💻 Après connexion, Django redirige vers /accounts/profile/ et affiche une 404. Comment corriger ça ?
Créer une vue profile qui affiche une page vide
Ajouter LOGIN_REDIRECT_URL = '/' dans settings.py
Modifier le template login.html pour changer la destination
✓ LOGIN_REDIRECT_URL dans settings.py contrôle la destination après connexion. Par défaut Django cherche /accounts/profile/ qui n'existe pas dans nos projets.
