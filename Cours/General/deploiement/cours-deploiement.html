00 — Pourquoi ne pas déployer directement en production ?
→
Le problème du "ça marche sur ma machine"

Quand tu développes sur ton ordinateur, tu es dans un environnement contrôlé et privé — ton propre système d'exploitation, ta propre base de données, tes propres fichiers. Un serveur de production est un environnement différent : autre OS, autre BDD, autres variables, potentiellement des milliers d'utilisateurs simultanés.

Déployer directement de "local" en "prod" sans passer par une étape intermédiaire, c'est comme pousser une voiture non testée directement sur l'autoroute. Si elle tombe en panne, tous tes utilisateurs en subissent les conséquences.

💡 La solution — un pipeline à 3 étapes : local (développement), pré-production (test en conditions réelles), production (public). Chaque étape a un rôle précis.

01 — Comment fonctionne un nom de domaine
🌐
L'annuaire d'internet — le DNS

Ton serveur est identifié par une adresse IP — une suite de chiffres comme 162.55.12.48. Personne ne mémorise des adresses IP. Le DNS (Domain Name System) est l'annuaire qui fait la traduction entre monprojet.com et 162.55.12.48.

Quand tu tapes monprojet.com dans ton navigateur, voici ce qui se passe en coulisses en moins d'une seconde :

🖥️ Ton navigateur
→
🔍 Résolveur DNS
(ton FAI ou 8.8.8.8)
→
🌳 Serveur Racine
« qui gère .com ? »
✅ IP : 162.55.12.48
←
🏷️ Serveur autoritaire
chez ton registrar
←
📋 Serveur TLD .com
« ton registrar gère ça »
↓
🖥️ Ton serveur 162.55.12.48
Django tourne ici
⏱️ La propagation DNS — quand tu achètes un domaine et le pointes vers un serveur, le changement prend de quelques minutes à 48 heures à se propager sur tous les serveurs DNS du monde. C'est normal — patience lors du premier déploiement.
📋
Anatomie d'un nom de domaine
Décomposition de : blog.monprojet.com
blog.monprojet.com

blog → Sous-domaine — partie que tu contrôles librement. www, api, staging, admin…
monprojet → Domaine — le nom que tu achètes chez un registrar (~10€/an)
com → TLD (Top Level Domain) — extension gérée par une autorité. .fr, .io, .dev, .app…
Type d'enregistrement DNSRôleExemple
A recordPointe un domaine vers une adresse IPv4monprojet.com → 162.55.12.48
AAAA recordPointe vers une adresse IPv6monprojet.com → 2001:db8::1
CNAME recordAlias — pointe vers un autre domainewww → monprojet.com
TXT recordDonnées texte — vérification, SPF email…v=spf1 include:railway.app
🎯 Sur Railway / Render, tu ajoutes un CNAME record qui pointe www.monprojet.com vers leur domaine (xxx.up.railway.app). Ils gèrent ensuite la résolution vers l'IP réelle du serveur. Si l'IP change, ton domaine suit automatiquement.
02 — Préparer son projet Django pour le déploiement
⚙️
Ce qui doit changer entre local et serveur

Un projet Django qui tourne en local a plusieurs réglages "dangereux" activés pour faciliter le développement. Avant de déployer, ces réglages doivent être corrigés.

⚙️settings.py — local (DANGEREUX en prod)Ce qu'il ne faut PAS mettre en ligne 
# ❌ Debug activé → affiche le code source en cas d'erreur
DEBUG = True

# ❌ Clé secrète en clair dans le code
SECRET_KEY = 'django-insecure-ma-super-cle-secrete-123'

# ❌ Pas de restriction sur les hôtes autorisés
ALLOWED_HOSTS = []

# ❌ SQLite — pas adapté à plusieurs utilisateurs simultanés
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.sqlite3',
        'NAME': BASE_DIR / 'db.sqlite3',
    }
}
✅settings.py — production (version sécurisée)Lire depuis les variables d'environnement
settings.py 
import os
import dj_database_url   # pip install dj-database-url
from decouple import config  # pip install python-decouple

# ✅ Lire depuis le fichier .env ou les variables du serveur
SECRET_KEY = config('SECRET_KEY')
DEBUG      = config('DEBUG', default=False, cast=bool)

ALLOWED_HOSTS = config('ALLOWED_HOSTS', default='').split(',')

# ✅ PostgreSQL en prod (SQLite en local si DATABASE_URL absent)
DATABASES = {
    'default': dj_database_url.config(
        default='sqlite:///db.sqlite3',
        conn_max_age=600
    )
}

# ✅ Fichiers statiques — WhiteNoise sert les fichiers en prod
STATIC_ROOT = BASE_DIR / 'staticfiles'
STATIC_URL  = '/static/'
STATICFILES_STORAGE = 'whitenoise.storage.CompressedManifestStaticFilesStorage'

# ✅ HTTPS en production
if not DEBUG:
    SECURE_SSL_REDIRECT         = True
    SESSION_COOKIE_SECURE       = True
    CSRF_COOKIE_SECURE          = True
    SECURE_HSTS_SECONDS         = 31536000
    SECURE_HSTS_INCLUDE_SUBDOMAINS = True
.env (fichier LOCAL, jamais committé sur Git) 
# Fichier .env — à la racine du projet, jamais dans Git
SECRET_KEY=ma-vraie-cle-secrete-longue-et-unique
DEBUG=True
ALLOWED_HOSTS=localhost,127.0.0.1
# En local, pas de DATABASE_URL → Django utilise SQLite
🚨 Ajouter .env dans .gitignore immédiatement — une seule fois sur GitHub public suffit pour que des robots collectent ta clé secrète et compromettent ton projet. Le fichier .env ne doit jamais voyager ailleurs que sur ton ordinateur.

✓Base de données PostgreSQL incluse

04 — Connecter un nom de domaine personnalisé
🌐Acheter et configurer un domaineDe OVH/Namecheap vers Railway

Ton projet tourne sur xxx.up.railway.app. Pour avoir monprojet.com, il faut :

Acheter un domaineChez un registrar : OVH (fr), Namecheap, Porkbun (pas cher), Google Domains. ~10€/an pour un .com, ~7€ pour un .fr.
Dans Railway : ajouter le domaine personnaliséSettings → Domains → Add Custom Domain → entrer monprojet.com. Railway te donne un enregistrement CNAME à configurer.
Dans ton registrar : configurer le DNSZone DNS → ajouter un enregistrement :
Type: CNAME | Nom: www | Valeur: xxx.up.railway.app
Et pour le domaine nu (monprojet.com sans www) : ajouter un A record vers l'IP fournie par Railway.
Mettre à jour ALLOWED_HOSTS dans les variables RailwayALLOWED_HOSTS=monprojet.com,www.monprojet.com,xxx.up.railway.app
Attendre la propagation DNS + validation HTTPSRailway génère automatiquement un certificat SSL (Let's Encrypt). La propagation DNS peut prendre 15 min à 48h. Vérifiable avec https://dnschecker.org.
05 — Le pipeline local → pré-prod → prod en pratique
🔄
Pourquoi ce pipeline — le raisonnement

Ce n'est pas du formalisme. Chaque étape résout un problème réel :

ÉtapeCe qu'on testePourquoi c'est indispensable
Local La logique, le code, les fonctionnalités Itération rapide sans conséquences. Erreur → correction immédiate. SQLite suffit car tu es seul.
Pré-prod La configuration serveur, les variables d'env., les migrations PostgreSQL Détecte les problèmes spécifiques au serveur (différences OS, permissions, variables manquantes) avant que les vrais utilisateurs les voient.
Production Performance sous charge, monitoring, sauvegardes On ne déploie en prod que ce qui a été validé en pré-prod. Les utilisateurs ne subissent jamais les bugs de développement.
🔄Workflow quotidien avec GitComment ça se passe concrètement

Sur Railway et Render, la pré-prod et la prod sont deux environnements séparés liés à des branches Git différentes. Pousser sur main déclenche le déploiement en prod, pousser sur staging met à jour la pré-prod.

Terminal — Workflow quotidien 
# ── 1. Développer en local ──────────────────────
git checkout -b feature/ajout-commentaires
# ... coder, tester en local sur localhost:8000 ...
git add .
git commit -m "feat: ajouter les commentaires sur les articles"

# ── 2. Pousser en pré-prod (branche staging) ────
git push origin feature/ajout-commentaires
git checkout staging
git merge feature/ajout-commentaires
git push origin staging
# → Railway déploie automatiquement sur staging.monprojet.com
# → Tester manuellement, faire tester à l'équipe / au client

# ── 3. Déployer en production (branche main) ─────
git checkout main
git merge staging
git push origin main
# → Railway déploie automatiquement sur monprojet.com
# → Vérifier les logs → surveiller les erreurs les 30 prochaines min
🛡️ La règle absolue — on ne modifie jamais directement la branche main (production). Tout passe par des branches de fonctionnalités → pré-prod → prod. En cas de bug critique en prod, on fait un hotfix dédié.
06 — Après le déploiement — ce qu'on surveille
🔍
Les vérifications post-déploiement
Tester toutes les pages critiquesPage d'accueil, connexion/déconnexion, formulaires, paiement si présent. Ne jamais supposer que "ça marche" — vérifier manuellement.
Vérifier le HTTPSL'URL doit commencer par https://. Le cadenas vert = certificat SSL valide. Si http:// → configurer la redirection dans Django (SECURE_SSL_REDIRECT = True).
Lire les logs en temps réelRailway / Render → onglet Logs. Chercher des 500 Internal Server Error, des erreurs de migration, des imports manquants.
Tester en navigation privéeLes cookies de développement local peuvent masquer des problèmes d'authentification. Tester dans une fenêtre privée simule un nouvel utilisateur.
Vérifier les fichiers statiquesCSS et JS bien chargés ? Images présentes ? Si des ressources manquent : vérifier que collectstatic s'est bien exécuté et que WhiteNoise est dans MIDDLEWARE.
⚠️
Erreurs fréquentes au premier déploiement
