📁 Structure d'un projet Django

Chaque fichier, son rôle, son importance — comprendre l'architecture avant de coder.

Django 4.x / 5.x Architecture 12 fichiers clés ~30 min
Vue d'ensemble
📁
Pourquoi comprendre la structure ?

Quand on débute avec Django, on crée un projet et on se retrouve face à une dizaine de fichiers générés automatiquement. Sans comprendre à quoi sert chacun, on est vite perdu — on ne sait pas où écrire son code, ni pourquoi ça plante.

Ce cours vous fait visiter chaque fichier et dossier, de la racine jusqu'aux apps, avec le rôle exact de chacun et les erreurs classiques associées.

🗺️ Analogie — Un projet Django c'est comme un restaurant. settings.py est le règlement intérieur, urls.py est le plan de table, models.py est la carte des plats, views.py est le chef cuisiner, et les templates/ sont la présentation dans l'assiette.
🌲
La commande qui créer la base du projet

Deux commandes génèrent l'arborescence minimum d'un projet Django :

# 1. Crée le dossier projet (settings, urls, wsgi, asgi...)
django-admin startproject monprojet

# 2. Crée une app (models, views, admin, migrations...)
python manage.py startapp blog

Un aperçu d'un arborescence avancé, les éléments colorés seront expliqué dans ce cours :

monprojet/
├── manage.py          # ① Chef d'orchestre
│
├── monprojet/         # Dossier de config du projet
│   ├── settings.py    # ② Cerveau de la config
│   ├── urls.py        # ③ Plan des routes du projet
│   ├── wsgi.py        # ④ Déploiement classique
│   └── asgi.py        # ⑤ Déploiement async
│
└── blog/              # Dossier de l'app
    ├── models.py      # ⑥ Schéma de la BDD
    ├── views.py       # ⑦ Logique des pages
    ├── urls.py        # ⑧ Routes de l'app
    ├── admin.py       # ⑨ Interface admin
    ├── apps.py        # ⑩ Config de l'app
    ├── tests.py       # ⑩ Vérification de l'app
    ├── migrations/    # ⑪ Historique BDD
    ├── templates/     # ⑫ Fichiers HTML
    └── static/        # ⑬ CSS, JS, images
⚠️ ATTENTION Certains éléments comme les dossiers templates/, static/ ou certains fichiers urls.py, tests.py et d'autres doivent être créés manuellement.
Partie 1 — La racine du projet
🎛️ manage.py Le chef d'orchestre Indispensable

manage.py est le couteau suisse de Django. C'est lui qu'on appelle dans le terminal pour toutes les opérations de gestion du projet. Il est à la racine — jamais dans un sous-dossier.

Ce qu'on fait avec lui

CommandeCe qu'elle fait
python manage.py runserverLance le serveur de développement local
python manage.py makemigrationsPrépare les modifications de BDD
python manage.py migrateApplique les modifications en BDD
python manage.py startapp blogCrée une nouvelle application
python manage.py createsuperuserCrée un compte administrateur
python manage.py shellOuvre un interpréteur Python avec Django chargé
⚠️ Toujours depuis le dossier racine — manage.py doit être lancé depuis le dossier qui le contient. Si votre terminal est au mauvais endroit, vous obtenez une erreur No such file or directory.
Partie 2 — Le dossier de configuration
⚙️ settings.py Le cerveau de la configuration Critique

settings.py est le fichier de configuration central. Il dit à Django comment se comporter : quelle base de données utiliser, quelles apps sont actives, où trouver les templates, etc. Si ce fichier est mal configuré, le projet ne démarre pas.

Les sections les plus importantes

monprojet/settings.py 
# Toutes les apps actives — votre app doit être ici
INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    ...
    'blog',  # ← votre app
]

# Base de données — SQLite par défaut (parfait pour débuter)
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.sqlite3',
        'NAME': BASE_DIR / 'db.sqlite3',
    }
}

# Langue et fuseau horaire
LANGUAGE_CODE = 'fr-fr'
TIME_ZONE = 'Europe/Paris'

# Fichiers statiques (CSS, JS, images)
STATIC_URL = '/static/'

# Redirection après connexion
LOGIN_REDIRECT_URL = '/'
🍝 Effet spaghetti classique — Oublier d'ajouter votre app dans INSTALLED_APPS. Résultat : les migrations ne trouvent pas vos models, les templates ne sont pas détectés, tout semble planter sans raison apparente.
🗺️ monprojet/urls.py Le routeur principal Critique

C'est le point d'entrée de toutes les URLs du site. Il ne gère pas directement les routes des apps — il délègue aux urls.py des apps avec include().

monprojet/urls.py 
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('blog/', include('blog.urls')),      # délègue à l'app
    path('accounts/', include('django.contrib.auth.urls')),
]
💡 Règle d'or — Ce fichier ne contient que des include(). Les vraies routes (vers les views) sont dans le urls.py de chaque app.
🚀 wsgi.py & asgi.py Déploiement en production Avancé

Ces deux fichiers sont les portes d'entrée pour déployer Django sur un vrai serveur. En développement, on ne les touche pas — c'est manage.py runserver qui s'en charge.

FichierUsageQuand ?
wsgi.pyServeurs classiques (Gunicorn, Apache)Déploiement standard
asgi.pyServeurs async (Daphne, Uvicorn)WebSockets, temps réel
📌 Pour débuter — Ignorez ces fichiers pour l'instant. Ils ne vous concernent qu'au moment de mettre votre site en ligne sur un serveur réel.
Partie 3 — Le dossier de l'application
🗄️ blog/models.py Le schéma de la base de données Indispensable

C'est ici que vous décrivez vos données. Chaque classe Python = une table en base de données. Django lit ces classes et crée les vraies tables SQL via les migrations.

blog/models.py 
from django.db import models

class Article(models.Model):
    titre    = models.CharField(max_length=200)
    contenu  = models.TextField()
    publie   = models.BooleanField(default=False)
    date     = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.titre
⚠️ Règle absolue — Après chaque modification de models.py, il faut obligatoirement lancer python manage.py makemigrations puis python manage.py migrate. Sans ça, la vraie base de données n'est pas mise à jour.
⚙️ blog/views.py La logique de chaque page Indispensable

Les views sont les chefs cuisiniers du projet. Chaque function reçoit une requête HTTP, fait ce qu'elle doit faire (récupérer des données, vérifier des permissions…), puis renvoie une réponse — généralement un template HTML rempli de données.

blog/views.py 
from django.shortcuts import render
from .models import Article

def liste_articles(request):
    articles = Article.objects.filter(publie=True)
    return render(request, 'blog/liste.html', {'articles': articles})
Flow d'une view
Reçoit la requête → Interroge le model → Prépare les données → Renvoie le template rempli
🔗 blog/urls.py Les routes de l'app Indispensable

Ce fichier est à créer manuellement — Django ne le génère pas. Il contient les routes spécifiques à l'app et est inclus depuis le urls.py du projet via include().

blog/urls.py — À créer manuellement 
from django.urls import path
from . import views

app_name = 'blog'

urlpatterns = [
    path('',             views.liste_articles, name='liste'),
    path('<int:pk>/',   views.detail_article, name='detail'),
]
🚨 Piège classique — Ne pas oublier de relier ce fichier depuis monprojet/urls.py avec include('blog.urls'). Sinon Django ne trouvera jamais les routes de votre app.
🛠️ blog/admin.py L'interface d'administration Important

Django génère automatiquement une interface d'administration complète à l'adresse /admin/. Pour qu'un model y apparaisse, il suffit de l'enregistrer dans ce fichier.

blog/admin.py 
from django.contrib import admin
from .models import Article

# Enregistrement simple
admin.site.register(Article)

# Enregistrement personnalisé — affiche titre, date et statut
@admin.register(Article)
class ArticleAdmin(admin.ModelAdmin):
    list_display = ['titre', 'date', 'publie']
    list_filter  = ['publie']
    search_fields = ['titre']
📋 blog/apps.py Configuration de l'app Secondaire

Créé automatiquement par Django, ce fichier déclare la configuration de l'app. En pratique, on ne le modifie presque jamais quand on débute.

blog/apps.py 
from django.apps import AppConfig

class BlogConfig(AppConfig):
    default_auto_field = 'django.db.models.BigAutoField'
    name = 'blog'
📌 Dans INSTALLED_APPS, vous pouvez écrire 'blog' (raccourci) ou 'blog.apps.BlogConfig' (chemin complet). Les deux fonctionnent.
Partie 4 — Les dossiers spéciaux
📜 blog/migrations/ L'historique de la base de données Important

Ce dossier contient l'historique complet de toutes les modifications de votre base de données. Chaque fois que vous modifiez un model et lancez makemigrations, un nouveau fichier est créé ici.

Structure typique de migrations/ 
migrations/
├── __init__.py
├── 0001_initial.py          # Création des tables
├── 0002_article_slug.py     # Ajout du champ slug
└── 0003_article_auteur.py   # Ajout de la relation auteur
💡 Ne supprimez jamais les fichiers de migration à la main. Django les utilise pour savoir dans quel état est votre BDD. Si vous devez tout remettre à zéro, il existe des commandes prévues pour ça.
🎨 templates/ Les fichiers HTML Important

Le dossier templates/ contient tous les fichiers HTML de l'app. Django les cherche selon une convention de nommage précise : templates/nom_app/nom_template.html.

Organisation recommandée 
blog/
└── templates/
    └── blog/                   # sous-dossier = nom de l'app
        ├── base.html            # template parent (layout commun)
        ├── article_list.html    # liste des articles
        └── article_detail.html  # détail d'un article
🔑 Le sous-dossier est obligatoire — Sans templates/blog/, Django peut confondre des templates de même nom entre différentes apps. Toujours nommer le sous-dossier comme l'app.
🎭 static/ CSS, JavaScript, images Important

Les fichiers statiques — tout ce qui ne change pas selon l'utilisateur — vont dans static/. CSS, JavaScript, polices, images de design.

Organisation recommandée 
blog/
└── static/
    └── blog/                # sous-dossier = nom de l'app
        ├── css/
        │   └── style.css
        ├── js/
        │   └── main.js
        └── img/
            └── logo.png
Dans un template — charger un fichier statique 
{% load static %}
<link rel="stylesheet" href="{% static 'blog/css/style.css' %}">
