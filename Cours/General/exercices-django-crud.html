Concepts clés du CRUD
CRUD↻
Create · Read · Update · Delete — les 4 opérations fondamentales de tout site web
ModelForm↻
Génère automatiquement un formulaire HTML depuis un model Django — avec validation incluse
form.save(commit=False)↻
Crée l'objet Python sans l'écrire en BDD — permet d'ajouter des champs comme auteur avant
instance=article↻
Paramètre clé du Update — pré-remplit le formulaire avec les données existantes et met à jour l'article
form.is_valid()↻
Vérifie que toutes les données du formulaire respectent les règles du model — retourne True ou False
article.delete()↻
Supprime l'objet de la base de données — toujours déclenché par une requête POST, jamais GET
fields = ['titre', ...]↻
Dans la classe Meta du ModelForm — liste explicite des champs à afficher. Jamais '__all__'
messages.success()↻
Envoie un message flash à afficher dans le template après une action réussie (création, suppression…)
article.auteur != request.user↻
Vérification de sécurité dans Update et Delete — seul l'auteur peut modifier ou supprimer son article
{% csrf_token %}↻
Obligatoire dans tous les formulaires POST — protège contre les attaques CSRF

Distingue l'affichage du formulaire (GET) de sa soumission (POST) dans les vues Create et Update

04 — Scénarios
Scénario 1
🧑‍💻 Vous avez un ModelForm avec fields = '__all__'. Un utilisateur malveillant inspecte votre HTML et soumet le formulaire avec un champ auteur modifié. Que risque-t-il de se passer ?
Django ignore automatiquement les champs non autorisés
L'utilisateur peut s'attribuer des articles appartenant à d'autres — faille de sécurité
Le formulaire lève une erreur de validation automatiquement
✓ fields = '__all__' expose tous les champs du model — y compris auteur. Listez toujours explicitement les champs autorisés avec fields = ['titre', 'contenu', 'publie'] et ajoutez auteur manuellement via save(commit=False).
Scénario 2
🧑‍💻 Dans votre vue de modification, vous écrivez form = ArticleForm(request.POST) au lieu de ArticleForm(request.POST, instance=article). Que se passe-t-il ?
L'article existant est mis à jour normalement
Un nouvel article est créé au lieu de modifier l'existant — doublon en BDD
Django lève une erreur car l'article existe déjà
✓ Sans instance=article, Django ne sait pas quel objet mettre à jour — il en crée un nouveau. Le paramètre instance est la clé qui transforme un Create en Update.
Scénario 3
🧑‍💻 Pour supprimer un article, vous créez un simple lien <a href="/blog/42/supprimer/">Supprimer</a> sans formulaire POST. Un moteur de recherche indexe votre site. Que risque-t-il d'arriver ?
Rien — les moteurs de recherche n'exécutent pas les liens de suppression
Le robot suit le lien avec une requête GET et supprime l'article sans que personne ne clique
Django refuse automatiquement les suppressions via GET
✓ Les robots d'indexation suivent tous les liens. La suppression via GET est dangereuse — n'importe qui ou n'importe quoi peut déclencher l'action. Toujours utiliser un formulaire POST avec {% csrf_token %}.
Scénario 4
🧑‍💻 Dans la vue modifier_article, vous avez oublié la vérification if article.auteur != request.user: redirect(). Un utilisateur connecté connaît l'URL /blog/42/modifier/. Que peut-il faire ?
Modifier l'article de quelqu'un d'autre en tapant directement l'URL
Rien — Django vérifie automatiquement la propriété de l'article
Il voit une erreur 403 car il n'est pas l'auteur
✓ @login_required vérifie qu'on est connecté, mais pas qu'on est le bon utilisateur. La vérification article.auteur != request.user est indispensable dans toutes les vues Update et Delete.

06 — Remettre dans l'ordre
↕️
Flow complet d'une vue Create

Glissez-déposez ces étapes dans le bon ordre d'exécution quand un utilisateur soumet le formulaire de création.

⠿? article.save() — sauvegarde en BDD
⠿? Le navigateur envoie une requête POST
⠿? redirect() vers la page de détail
⠿? form.is_valid() — validation des données
⠿? ArticleForm(request.POST) — instancier le form
⠿? form.save(commit=False) + article.auteur = request.user
