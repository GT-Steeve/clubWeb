🐍 Débuter avec Django

Environnement virtuel, models, views, urls — les fichiers essentiels reliés pas à pas.

Django 4.x / 5.x Pratique Fil rouge : Blog ~40 min
00 — Avant tout : l'environnement virtuel
🧪 Terminal À faire une seule fois, au tout début

Avant d'écrire la moindre ligne de Django, vous devez préparer un environnement virtuel. C'est une étape que beaucoup de débutants sautent — et qui provoque des bugs mystérieux des semaines plus tard.

Terminal — dans votre dossier de projets 
# Préparation de l'environnement de programmation
python --version        # Vérifie que Python est installé
mkdir monprojet-django  # Créer le dossier du projet
cd monprojet-django

python -m venv env      # Réserve un espace de code isolé

# Windows — activer l'environnement
.\env\Scripts\activate

# macOS / Linux — activer l'environnement
source env/bin/activate

# Une fois activé, installer Django dans cet environnement
pip install django

# Vérifier l'installation
django-admin --version

Pourquoi un environnement virtuel ?

Imaginez votre ordinateur comme un appartement. Sans environnement virtuel, tous vos projets Python cohabitent dans le même salon — ils partagent les mêmes bibliothèques, les mêmes versions. Si un projet a besoin de Django 4.2 et un autre de Django 5.0, ils se marchent dessus. L'un finit par casser l'autre.

Un environnement virtuel, c'est comme donner un appartement privé à chaque projet. Chaque projet installe exactement ce dont il a besoin, dans la version qu'il veut, sans interférer avec les voisins.

📦 Ce que fait python -m venv env — Cette commande crée un dossier env/ avec une copie isolée de Python, un gestionnaire pip privé, et un dossier site-packages/ dédié. Tout ce que vous installez après activation va uniquement dans ce dossier, pas sur le reste du système.

Comment savoir si l'environnement est actif ?

Quand l'environnement est activé, votre terminal affiche son nom entre parenthèses :

# Environnement NON activé
user@machine monprojet-django %

# Environnement ACTIVÉ — (env) apparaît à gauche
(env) user@machine monprojet-django %

Si vous ne voyez pas (env), relancez la commande d'activation avant de continuer.

Le fichier requirements.txt

Avant de partager votre projet, sauvegardez la liste exacte des bibliothèques installées :

# Sauvegarder les dépendances
pip freeze > requirements.txt

# Contenu typique :
# Django==5.0.4
# sqlparse==0.5.0
# asgiref==3.8.1

# Réinstaller sur un autre ordinateur
pip install -r requirements.txt
🗂️ Toujours ajouter env/ dans votre .gitignore — Le dossier peut peser plusieurs centaines de Mo. Committez uniquement requirements.txt : n'importe qui pourra recréer l'environnement exact en une commande.
🍝 Effet spaghetti classique — Vous installez Django globalement. Deux mois plus tard, vous mettez à jour Django pour un autre projet. Votre premier projet plante. Vous cherchez le bug dans votre code pendant des heures — alors que le problème est un conflit de version entièrement extérieur. L'environnement virtuel est votre première ligne de défense.

01 — models.py
🗄️ blog/models.py Le schéma de votre base de données

models.py est votre dictionnaire de données. Chaque classe Python = une table en base de données. Vous décrivez les champs, Django crée la table tout seul via les migrations.

Anatomie d'un Model

blog/models.py 
from django.db import models
from django.utils import timezone

class Article(models.Model):
    titre      = models.CharField(max_length=200)
    contenu    = models.TextField()
    auteur     = models.CharField(max_length=100)
    publie_le  = models.DateTimeField(default=timezone.now)
    publie     = models.BooleanField(default=False)

    class Meta:
        ordering = ['-publie_le']  # plus récent en premier

    def __str__(self):
        return self.titre  # affiché dans l'admin

Les types de champs essentiels

Champ DjangoUsage
CharField(max_length=N)Texte court — titre, nom…
TextField()Texte long — article, bio…
BooleanField()Vrai / Faux
DateTimeField()Date + heure
IntegerField()Entier
ForeignKey()Lien vers une autre table
ImageField()Upload d'image

Ajouter une relation — Catégorie

blog/models.py 
class Categorie(models.Model):
    nom = models.CharField(max_length=50)

    def __str__(self):
        return self.nom

class Article(models.Model):
    titre     = models.CharField(max_length=200)
    contenu   = models.TextField()
    categorie = models.ForeignKey(
        Categorie,
        on_delete=models.CASCADE,  # si catégorie supprimée → articles aussi
        null=True, blank=True
    )

Après chaque modification du model

# 1. Créer la migration (photo du schéma)
python manage.py makemigrations

# 2. Appliquer la migration (modifier la vraie BDD)
python manage.py migrate
🍝 Effet spaghetti — models.py — Vous copiez un model IA sans comprendre les types de champs, vous oubliez makemigrations. Résultat : la BDD n'est pas à jour, les données ne s'enregistrent pas, vous cherchez le bug des heures alors que le code « marche ».
02 — views.py
⚙️ blog/views.py La logique de chaque page

views.py contient les fonctions qui traitent une requête HTTP et retournent une réponse. C'est ici que vous récupérez les données depuis les models et les transmettez au template.

Vue simple — liste d'articles

blog/views.py 
from django.shortcuts import render, get_object_or_404
from .models import Article

def liste_articles(request):
    articles = Article.objects.filter(publie=True)
    contexte = {
        'articles': articles,
        'titre_page': 'Mon Blog',
    }
    return render(request, 'blog/article_list.html', contexte)
Ce que fait cette vue
1. Reçoit la requête HTTP
2. Interroge la BDD : articles où publie=True
3. Prépare un dictionnaire "contexte"
4. Envoie ce contexte au template HTML
5. Retourne la réponse HTTP

Vue de détail avec paramètre d'URL

blog/views.py 
def detail_article(request, pk):
    # Renvoie une 404 si l'article n'existe pas
    article = get_object_or_404(Article, pk=pk, publie=True)
    return render(request, 'blog/article_detail.html', {'article': article})

Les méthodes ORM les plus utiles

# Tous les articles
Article.objects.all()

# Filtrer
Article.objects.filter(publie=True)
Article.objects.filter(auteur='Alice', publie=True)

# Exclure
Article.objects.exclude(publie=False)

# Un seul objet (exception si absent)
Article.objects.get(pk=1)

# Trier — le tiret = décroissant
Article.objects.order_by('-publie_le')

# Limiter aux 5 premiers
Article.objects.all()[:5]

# Créer
Article.objects.create(titre='Mon titre', contenu='...')
💡 FBV vs CBV — Il existe deux styles : les Function-Based Views (FBV) et les Class-Based Views (CBV). Commencez par les FBV — elles sont lisibles, explicites, faciles à déboguer. Les CBV apportent des raccourcis puissants une fois les bases comprises.
03 — urls.py
🗺️ blog/urls.py Le plan des routes de l'app

urls.py fait le lien entre une URL tapée dans le navigateur et la vue Python qui doit répondre.

📁 Ce fichier n'existe pas par défaut dans l'app ! Django ne crée pas blog/urls.py automatiquement. Vous devez le créer à la main.
blog/urls.py — À CRÉER MANUELLEMENT 
from django.urls import path
from . import views  # importe les vues du même dossier

app_name = 'blog'  # namespace pour les liens dans les templates

urlpatterns = [
    # /blog/  → liste_articles
    path('', views.liste_articles, name='liste'),

    # /blog/42/  → detail_article avec pk=42
    path('<int:pk>/', views.detail_article, name='detail'),
]

Les convertisseurs de types dans les URLs

SyntaxeCaptureExemple
<int:pk>Entier/blog/42/ → pk=42
<str:slug>Texte sans //blog/mon-article/
<slug:slug>Lettres, chiffres, - _/blog/mon-article-2024/
🔗 monsite/urls.py Relier le routeur principal à l'app

Le urls.py du projet doit connaître votre app. On utilise include() pour déléguer les URLs commençant par /blog/.

monsite/urls.py — MODIFIER CE FICHIER 
from django.contrib import admin
from django.urls import path, include  # ← ajouter include

urlpatterns = [
    path('admin/', admin.site.urls),

    # Toute URL commençant par /blog/ → confiée à blog/urls.py
    path('blog/', include('blog.urls')),
]
Ce que ça donne
/blog/ → liste_articles
/blog/42/ → detail_article (pk=42)
/admin/ → interface d'administration Django
✅ Bonne pratique — Ne mettez pas toutes vos routes dans le urls.py du projet. Chaque app a le sien, reliés avec include(). Code modulaire et maintenable.
04 — Les templates HTML
🎨 templates/blog/article_list.html Afficher les données

Les templates Django utilisent le Django Template Language (DTL). Les variables du contexte sont accessibles avec {{ }} et la logique avec {% %}.

templates/blog/article_list.html 
<!-- Héritage de template -->
{% extends "base.html" %}

{% block content %}

<h1>{{ titre_page }}</h1>

{% for article in articles %}
  <article>
    <h2><a href="{% url 'blog:detail' article.pk %}">
      {{ article.titre }}
    </a></h2>
    <p>Par {{ article.auteur }} — {{ article.publie_le|date:"d/m/Y" }}</p>
    <p>{{ article.contenu|truncatewords:30 }}</p>
  </article>
{% empty %}
  <p>Aucun article publié.</p>
{% endfor %}

{% endblock %}
05 — settings.py & admin.py
⚙️ settings.py + admin.py Déclarer et exposer l'app

1. Déclarer l'app dans INSTALLED_APPS

monsite/settings.py 
INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',

    'blog',  # ← AJOUTER VOTRE APP ICI
]
🚨 Oubli n°1 des débutants — Ne pas ajouter l'app dans INSTALLED_APPS. Les migrations ne trouvent pas les models, les templates ne sont pas détectés, tout plante en silence.

2. Enregistrer les models dans admin.py

blog/admin.py 
from django.contrib import admin
from .models import Article, Categorie

admin.site.register(Article)
admin.site.register(Categorie)

3. Créer un super-utilisateur

python manage.py createsuperuser
# Entrez : username, email, password
# Puis : http://127.0.0.1:8000/admin/
